Every task below is delivered (✅). Each entry keeps only what the code cannot say for
itself: why the task existed, which decisions were deliberate, and which traps were
found the hard way.

**The code is the truth.** These cards were condensed from the original pre-implementation
guides, which described a design *before* it was built and had since drifted from it. The

## T001 — Project Setup & Dependencies ✅
**Why:** Establish the dependency and lint baseline before any feature code, so state management, location, sensors, background execution, ML, and persistence all build on the same foundation from the start.
**Durable decisions:**
- Riverpod with code generation (`flutter_riverpod` + `riverpod_annotation` + `riverpod_generator`) chosen as the state-management approach, not plain Riverpod or another library.
- Strict analyzer settings from the start (`strict-casts`, `strict-raw-types` in `analysis_options.yaml` — the modern replacement for the deprecated `implicit-casts`/`implicit-dynamic` strong-mode keys the guide originally specified).
- `*.g.dart` and `*.freezed.dart` excluded from analysis and (per T003) from git, since they're regenerated by `build_runner`.
- Platform-specific permission/manifest setup deliberately deferred out of this task (handled later, in permission and platform-config work).
**Delivered:** pubspec.yaml, analysis_options.yaml.
**Pitfalls:** TensorFlow Lite (`tflite_flutter`) needed platform-specific setup beyond the pub dependency; `permission_handler` likewise needed later platform wiring — both were intentionally punted rather than solved here.

## T002 — Feature-First Directory Structure ✅
**Why:** Establish a feature-first layout (data/domain/presentation per feature) before code accumulates, so features stay self-contained and concerns stay separated.
**Durable decisions:**
- Each feature owns its own `data/`, `domain/`, `presentation/` (trip_detection also has `services/`), rather than grouping by layer across the whole app.
- `lib/shared/` holds cross-feature code only (`models/`, `providers/`, `widgets/`), to avoid circular dependencies between features.
- `lib/core/` holds true app-wide utilities (constants, theme, utils) usable from anywhere.
**Delivered:** lib/core/constants, lib/core/theme, lib/core/utils, lib/features/{trip_detection,trip_history,settings,onboarding}, lib/shared/{models,providers,widgets}.
**Pitfalls:** empty directories aren't tracked by git, so placeholder `.gitkeep` files were needed in `shared/`.

## T003 — Riverpod Code Generation Setup ✅
**Why:** Wire up `build_runner` + `riverpod_generator` and settle the code-gen conventions (part directives, gitignore) before real providers get written, since nothing compiles without generated `.g.dart` files.
**Durable decisions:**
- `build.yaml` configures `riverpod_generator` with `explicit_to_json: true` for the project.
- Generated files (`*.g.dart`, `*.freezed.dart`) are gitignored and never committed — regenerated by `build_runner watch`/`build` instead.
- AutoDispose is the default for provider state; `keepAlive: true` reserved for persistent data (settings, active trip) — stated as a convention here, applied throughout later providers.
**Delivered:** build.yaml, .gitignore (g.dart/freezed.dart rules).
**Pitfalls:** a provider file needs its `part 'x.g.dart';` directive or it fails with an undefined `_$ClassName` error; a stale generated file after a provider signature change needs `--delete-conflicting-outputs` (or a `build_runner clean`) rather than a plain rebuild.

## T004 — Basic Location Service ✅
**Why:** AutoRide needed a foundational wrapper around `geolocator` so the rest of the app could read location without every feature talking to the platform plugin directly, and so permission state had a single owner.

**Durable decisions:**
- `LocationData` wraps a `geolocator` `Position` rather than exposing `Position` directly, keeping the platform type out of `domain/`.
- Location permission status is its own enum-backed provider (`LocationPermissionService`), separate from the location data provider, so UI can react to permission state without triggering a GPS read.
- The continuous-updates path is a plain `@riverpod` stream function (`locationStream`), not a class notifier — matches the repo-wide stream-provider convention documented in `provider_stream.dart`.
- Conservative defaults for this task (`LocationAccuracy.high`, 10 m distance filter) were deliberately left un-optimized; T006 owns battery tuning.

**Delivered:** `lib/features/trip_detection/domain/models/location_data.dart`, `lib/features/trip_detection/data/services/location_service.dart`, `lib/features/trip_detection/data/services/location_permission_service.dart`, `lib/features/trip_detection/data/services/location_utils.dart`.

**Pitfalls:** Emulators don't produce usable GPS — physical-device testing only. Always check/request permission before reading location; a `LocationServiceException` carries the `LocationPermissionStatus` so callers can branch on why it failed rather than parsing a message string.

## T005 — Background Location Tracking ✅
**Why:** Automatic trip detection has to survive the app being backgrounded or the OS trying to kill it, which on Android requires a foreground service with a persistent notification.

**Durable decisions:**
- The background isolate (`onStart` in `background_location_service.dart`) does **no location work of its own** — it only holds the Android foreground-service notification alive and relays text pushed from the main isolate via `service.invoke('updateNotification', …)`. The single source of truth for location is the foreground `locationStreamProvider`, consumed by the recorder and `TripDetectionCoordinator`. This is a deliberate correction (audit #7/#8, ledger L-007), not the original design.
- `BackgroundLocationService` is `@Riverpod(keepAlive: true)`, not autoDispose: its only consumer reads the notifier without watching it, so an autoDispose instance was torn down mid-`initialize()` and the foreground service silently never started — a race Android happened to win most of the time until it didn't.
- `initialize()` awaits `notificationServiceProvider.future` before configuring the service, because Android throws `CannotPostForegroundServiceNotificationException` if the notification channel doesn't exist yet when the service starts.
- Background location permission is requested progressively — foreground first, then always/background — because Android 11+ refuses to offer "Allow all the time" in the first-ask dialog.

**Delivered:** `lib/features/trip_detection/services/background_location_service.dart`, `requestBackgroundPermission`/`hasBackgroundPermission` on `LocationPermissionService` (`lib/features/trip_detection/data/services/location_permission_service.dart`), Android manifest permissions and the `location`-typed foreground service in `android/app/src/main/AndroidManifest.xml`, iOS `NSLocationAlwaysAndWhenInUseUsageDescription`/`UIBackgroundModes` in `ios/Runner/Info.plist`.

**Pitfalls:** Physical-device testing only — emulators don't exercise background services. iOS is more restrictive than Android and can terminate background location; document rather than fight it.

## T007 — Sensor Integration (Accelerometer/Gyroscope) ✅
**Why:** Needed a battery-safe abstraction over raw accelerometer/gyroscope streams as the foundation for cycling detection and for gating GPS on motion, without draining the battery.

**Durable decisions:**
- Detection uses vector magnitude (`sqrt(x²+y²+z²)`), not raw x/y/z — makes it independent of phone orientation (pocket, backpack, mount).
- The accelerometer is the pacer for the merged `MotionData` stream: one emission per accel sample carrying the most recent gyroscope reading (sample-and-hold), not one per either sensor — emitting on either doubled the effective rate and cost.
- Sampling rate is not a fixed constant: it's driven per power mode (`sensorSamplingRateNormal/Medium/Low/Critical` in `AppConstants`) via `PowerModeConfig`, and `sensor_service.dart` actively drops surplus samples to hold the OS-delivered rate down to the configured one, because Android/iOS round the requested period up on their own.
- Sensor streams are consumed through their Riverpod providers, never the generated functions directly, so tests can override and only one subscription is opened per sensor.
- Buffer is bounded to `AppConstants.sensorBufferSize` (3000 samples / 60s at 50Hz) to avoid unbounded memory growth.

**Delivered:** `lib/features/trip_detection/domain/models/motion_data.dart`, `lib/features/trip_detection/data/services/sensor_service.dart`, `lib/features/trip_detection/data/services/sensor_utils.dart`, `lib/features/trip_detection/data/services/motion_detection_service.dart`.

**Pitfalls:** Sensors don't work reliably in emulators — physical-device testing only. The requested sampling period is a request, not a contract: real hardware measured 55.6–83 Hz on a Pixel 6a and 51.4 Hz on an iPhone for a configured 50 Hz, so any rate-dependent logic must read the actual delivered rate from the audit heartbeat (`hb`), never assume the configured constant.

## T008 — Cycling Motion Pattern Detection ✅
**Why:** Distinguish cycling from walking/driving/running from motion data alone, as a rule-based stopgap explicitly meant to be swappable for an ML classifier later (T016-T019).

**Durable decisions:**
- Multi-layer confidence design (motion 40% / speed 35% / frequency 25%, `ActivityConfidence` model, threshold 0.6) was implemented as specified in `cycling_pattern_detector.dart`.
- Speed layer treats a missing GPS fix as a neutral 0.5 score rather than failing closed, so detection still works (at reduced confidence) without GPS.
- Interface was kept stream-based (`MotionWindow` + optional `LocationData` in, `ActivityConfidence` out) so a future ML classifier could be a drop-in replacement with the same contract.

**Delivered:** `lib/features/trip_detection/domain/models/activity_confidence.dart`, `lib/features/trip_detection/data/services/cycling_pattern_detector.dart`.

**Pitfalls:** This detector is fully implemented and test-covered but has **no call site in production** — grep confirms zero references outside its own file, only mentions in comments elsewhere. Its `currentLocation` field is declared but never assigned, so `speedScore` is permanently the hardcoded 0.5 neutral value — the speed layer never actually votes in this detector. The trip start decision actually shipped is `TripStartDetector`'s windowed accel+gyro fit (T050), a different, later implementation; do not assume this guide describes what runs today.

**Divergence found:** guide presents `CyclingPatternDetector` as the production cycling-detection mechanism feeding trip start/stop logic (see "Next Steps": T012/T013 integrating it). The code does not integrate it anywhere — trip start is decided by `TripStartDetector` (`lib/features/trip_detection/data/services/trip_start_detector.dart`), and the guide's target accuracy figures and its ML-replacement narrative describe a component that was built but never wired in.

## T009 — SQLite Database Schema ✅
**Why:** Needed local persistence for trip history and GPS route points, queryable for date ranges and route retrieval, without pulling in a heavier ORM.

**Durable decisions:**
- Timestamps stored as `INTEGER` (millisecondsSinceEpoch) rather than TEXT, for efficient range queries; booleans as `INTEGER` 0/1 (SQLite has no native boolean).
- `route_points.trip_id` has `ON DELETE CASCADE` with `PRAGMA foreign_keys = ON` set in `onConfigure` — deleting a trip removes its route points without app-level cleanup code.
- `DatabaseService.onConfigure`/`onCreate`/`onUpgrade` are public specifically so tests exercise the real production DDL/migration path against an in-memory database instead of re-declaring the schema (see comment tagged L-014).
- Migration steps are additive `ALTER TABLE ... ADD COLUMN` with explicit backfill defaults chosen to match the pre-migration semantics (e.g. `pause_duration` defaults to 0 because `duration` was already moving-time only).

**Delivered:** `lib/features/trip_detection/domain/models/trip.dart` (`Trip`, `RoutePoint`), `lib/features/trip_detection/data/services/database_service.dart`.

**Pitfalls:** Freezed private constructor must precede the factory constructor, and `toMap`/`fromMap` live in an extension, not inside the class — the usual freezed pitfall.

**Divergence found:** the guide's schema doc lists `trips` with 10 columns and 2 indexes on it; the shipped schema (`databaseVersion = 4`) has grown to 13 columns (`status`, `pause_duration`, `suspected_vehicle` added by v2/v3/v4 migrations) and 3 indexes on `trips` (adds `idx_trip_status`). These additions came from later tasks (trip lifecycle status L-068, pause tracking L-073, vehicle-veto flagging L-106), not from T009 itself, so the guide's static schema tables are stale for the current shape of the database.

## T010 — Trip Repository ✅
**Why:** T009 gave the app a SQLite schema; nothing yet turned Trip/RoutePoint domain models into rows, or gave callers a type-safe, transactional way to persist a ride.

**Durable decisions:**
- `saveTrip` writes the trip row and its route points inside one `Database.transaction`, so a ride and its GPS track are never left half-saved.
- `getAllTrips` never loads route points (a ride can carry hundreds); only `getTripById` joins them in, avoiding an N+1 query pattern across the trip list.
- All database exceptions are caught and rethrown as `TripRepositoryException`, so callers never see a raw `DatabaseException`.
- Multi-point writes (`saveRoutePoints`, and the points inside `saveTrip`) use `Database.batch()` rather than per-row inserts.
- `deleteTrip` relies on the schema's cascade delete rather than manually deleting route points first.

**Delivered:** lib/features/trip_history/data/repositories/trip_repository.dart, lib/features/trip_history/data/repositories/trip_repository.g.dart

**Pitfalls:** the guide's own pitfalls section (non-transactional saves, N+1 route-point loading, leaking `DatabaseException`, non-batched inserts) match what the shipped code avoids — treat them as the reasons for the decisions above, not new traps.

## T011 — Settings & Preferences ✅
**Why:** Detection, battery, location, notification, display and privacy behavior all needed user-configurable, persistent preferences instead of hardcoded defaults, with a reactive path into the services that already read `AppConstants`.

**Durable decisions:**
- Settings split into two freezed models — `DetectionSettings` and the umbrella `UserSettings` — persisted via SharedPreferences rather than a database, since this is small, flat, key-value state.
- `BatteryOptimizationMode` (aggressive/balanced/performance) is read by `battery_optimizer.dart`'s power-mode selection: performance always pins `PowerModeConfig.normal`, aggressive shifts the battery-level thresholds down, balanced keeps the original ladder — this is the one integration point wired at task time, deliberately left as the only one.
- Developer settings (`debugLoggingEnabled`, `showSensorOverlay`) are gated behind `kDebugMode` in the UI, not shipped to release users.
- Location/detection-sensitivity integration into the detector itself was explicitly deferred to when those features needed configuration, not built speculatively here.

**Delivered:** lib/features/settings/domain/models/, lib/features/settings/data/repositories/settings_repository.dart, lib/features/settings/data/services/settings_service.dart, lib/features/settings/presentation/providers/settings_provider.dart

**Pitfalls:** none beyond the standard freezed/Riverpod conventions already covered by the `freezed-riverpod-patterns` skill (sealed class, extensions outside the class, plain `Ref`).

## T012 — Trip State Machine ✅
**Why:** Trip detection needed a single, validated source of truth for the ride lifecycle (idle → detecting → active ↔ paused → idle) instead of ad hoc booleans scattered across detection code.

**Durable decisions:**
- `TripState` is a sealed freezed class (`idle`, `detecting`, `active`, `paused`); only `mapOrNull` transitions defined on `TripStateMachine` can move it, so an invalid transition (e.g. pausing from idle) is silently a no-op rather than a thrown error.
- `stateName` is a hand-spelled string per state, not derived from the generated `_Idle`/`_Active` runtime type name, because the exported audit log must stay readable across a code-generation change.
- Ending a trip funnels through one `_finishRecording` path so the foreground notification is always cancelled, even when the ride is `discarded` (too short, or too few route points) and must not fire a "trip recorded" notification.
- The end-of-trip notification reads the finalized `Trip` row the recorder just wrote (`finalTrip`), not a live metrics provider — reading the provider produced a stale or freshly-zeroed value, or skipped the notification while that provider was loading/erroring (L-069).

**Delivered:** lib/features/trip_detection/domain/models/trip_state.dart, lib/features/trip_detection/data/services/trip_state_machine.dart

**Pitfalls:** don't derive `stateName` from the freezed class name; don't read a live provider for the stop notification's numbers — both were tried and replaced for the reasons above.

## T014 — Automatic Trip Stop Detection ✅
**Why:** A trip must survive traffic lights and short stops without pausing, but a genuinely finished ride must still auto-stop rather than run forever — the detector has to tell the two apart from motion and GPS alone.

**Durable decisions:**
- Pause/stop are duration-gated: `AppConstants.minPauseDurationSeconds` (30s, plus `minConsecutiveStationaryDetections`) → pause; `maxPauseDurationSeconds` (300s) → stop; below 30s the trip just continues.
- Stationary verdict is a three-arm rule, not a flat speed/motion threshold: a fresh GPS fix (`stationaryGpsMaxAge`) at or above `movingSpeedMinKmh` (6 km/h) always means moving; below `stationarySpeedMaxKmh` (3 km/h) the fix only *admits* a stop and a windowed vibration check (`StationaryWindow.isVibrationFree`) has the final word (rotation is dropped there — a pocketed phone spins freely while the bike stands still); in the dead band or with no GPS, the sensor window decides alone.
- Resuming from pause requires movement sustained for `resumeMovementThresholdSeconds` (5s), not a single non-stationary sample — GPS speed at a true standstill is noisy.
- Clearing an *already-paused* trip's pause timer is gated on a real resume only (`tripIsPaused` disables the movement-hysteresis auto-clear used while still active) — without this, intermittent shuffling reset the auto-stop countdown forever without ever satisfying the resume rule, leaving a "zombie" pause.
- Sustained movement must persist `tripStopMovementHysteresisSamples` (3) counted readings before an active (not-yet-paused) trip's accumulating pause is cleared — a single transient reading must not reset the timer.

**Delivered:** `lib/features/trip_detection/data/services/trip_stop_detector.dart`, `lib/features/trip_detection/domain/models/trip_stop_state.dart`, `lib/features/trip_detection/data/services/stationary_window.dart`, relevant `AppConstants` (stationary*/movingSpeedMinKmh/tripStopMovementHysteresisSamples).

**Pitfalls:** An unthrottled verbose per-sample audit log of the stationary verdict produced 80k+ lines for 26 minutes of recording and pushed the file's own header out of the retention window (L-085) — the verdict emitter now throttles to `auditWindowVerdictInterval` and only always logs on verdict/source transitions. Downhill coasting (low pedaling motion, high speed) is protected from false-stopping because the GPS-speed arm outranks the vibration/rotation arms.

## T015 — Trip Data Recording ✅
**Why:** Turning a start/stop decision into actual trip data requires buffering GPS fixes, computing distance/duration/speed in real time, and persisting them without losing data or hammering the database on every fix.

**Durable decisions:**
- The trip row is created in the database first, and `TripStateMachine.startTripWithId(int)` takes the real DB id — no more temp/millisecond-based ids, so route points always reference a valid foreign key.
- Route points are filtered before being kept: `minRoutePointDistanceMeters` (15m, GPS-drift rejection), `maxLocationAccuracyMeters` (50m, reject poor fixes), `maxCyclingSpeedKmh` (60, outlier rejection) — all named `AppConstants`, not inline magic numbers.
- Buffered writes flush on three independent triggers — buffer reaching `routePointBufferSize` (100), a periodic timer at `maxRecordingIntervalSeconds` (30s), and trip stop — so a crash mid-ride loses at most ~30s of points.
- Fixes received before the start was confirmed are replayed through the exact same recording path (`_recordLocation`) rather than a separate code path, and the trip's `startTime` is retroactively moved back to the first surviving fix (L-076) — otherwise a ride would carry distance covered before confirmation but be timed as if it started later, corrupting duration and average speed. The backdate is clamped to never move `startTime` later (protects against a clock jump).
- `TripAlreadyStartingError` (a distinct `StateError` subtype) exists because two callers (the auto coordinator and a manual start button) can race `startRecording`; the loser must be told "a ride is already starting" rather than tearing down the winner's in-flight state (L-080).
- The recorder tracks a separate `_routePointsRecorded` cumulative counter distinct from the buffer's own length, because the buffer empties on every flush and would otherwise report 0 mid-ride (L-081).

**Delivered:** `lib/features/trip_detection/data/services/trip_recorder_service.dart`, `lib/features/trip_detection/data/services/trip_state_machine.dart`, `lib/features/trip_history/data/repositories/trip_repository.dart`, relevant `AppConstants` (minRoutePointDistanceMeters, routePointBufferSize, maxRecordingIntervalSeconds, maxLocationAccuracyMeters, maxCyclingSpeedKmh).

**Pitfalls:** Vehicle-speed evidence is fed to a `VehicleSpeedWatch` on every location update *outside* the pause guard and independent of recording filters (T051) — a car stopped at a red light is still a car, and speed evidence must accumulate even while the trip is paused; the watch used to end the ride outright on a speed spike but that cut short 8 real rides on 2026-09-09 (T053, L-106) and now only accumulates evidence rather than deciding.

## T020 — App Theme & Design System ✅
**Why:** The app needed one visual foundation (colors, type, spacing) before any real screens were built, so later UI work wouldn't invent ad hoc styling per screen.
**Durable decisions:**
- Deliberate cycling-oriented blue/teal primary + orange/amber secondary: energetic, motion-associated, high-visibility for safety-critical actions (start/stop).
- Semantic colors fixed to a meaning (success=green, warning=amber, error=red, info=blue) and reused for trip status (`tripActive`, `tripPaused`, `tripDetecting`) rather than inventing separate status colors.
- 8-point grid spacing (`AppSpacing.xs`..`xxl`) as the single spacing vocabulary, avoiding hardcoded padding values elsewhere.
- Typography via `google_fonts` (Roboto) for a consistent look across iOS/Android rather than relying on divergent system fonts.
- Theme mode (light/dark/system) persisted through `shared_preferences`, not just held in memory, so the choice survives restarts.
- Reusable stat/status widgets (`StatCard`, `StatusBadge`, `GradientContainer`, `EmptyState`) established early so feature screens share one look instead of each rolling its own.
**Delivered:** `lib/core/theme/` (app_colors.dart, app_text_styles.dart, app_spacing.dart, app_theme.dart, theme_provider.dart); `lib/shared/widgets/` (stat_card.dart, gradient_container.dart, status_badge.dart, empty_state.dart — plus error_view.dart and loading_view.dart added later, outside this task).
**Pitfalls:** `ColorScheme.background`/`onBackground` and `CardTheme` (vs `CardThemeData`), as used in the guide's proposed code, no longer compile against the Flutter/Material3 version in use — the shipped `app_theme.dart` drops `background`/`onBackground` entirely and uses `CardThemeData`.
The theme notifier class is `ThemeModeNotifier`, not `ThemeMode` as drafted — naming it `ThemeMode` would shadow Flutter's own `ThemeMode` enum, which the state type itself depends on.

## T021 — Onboarding Flow ✅
**Why:** First-launch users need context before AutoRide asks for location access — both to build trust and because Android 10+/iOS 14+ expect rationale before a permission prompt, not just a raw system dialog.
**Durable decisions:**
- Progressive disclosure: welcome → features → foreground location → background location → complete, education always before the permission ask.
- Background (always-on) location is optional and skippable — denial never blocks onboarding, since manual trip recording remains available without it.
- First-launch state persisted via `shared_preferences` (`AppConstants.onboardingCompleteKey`) so onboarding shows exactly once.
- Reuses the app's shared permission layer rather than inventing onboarding-specific request logic.
- A notification-permission step was added after background location (see Pitfalls) — the background design depends on notifications working, so onboarding is where that grant has to happen.
**Delivered:** `lib/features/onboarding/` (domain/models/onboarding_state.dart, data/services/onboarding_service.dart, presentation/providers/onboarding_provider.dart, presentation/screens/*, presentation/widgets/*), integrated at `lib/main.dart` as the initial route.
**Pitfalls:** The guide describes reusing `LocationPermissionService` directly; the shipped provider instead goes through `PermissionHandlerService`/`AppPermission` (`lib/core/permissions/services/permission_handler_service.dart`) and catches `PermissionPermanentlyDeniedException` to redirect to app settings — a case the guide never anticipated.
A third, undocumented step follows the background-permission screen: requesting notification permission (Android 13+ `POST_NOTIFICATIONS`), because without a runtime grant the foreground-service and trip notifications are silently suppressed.
Android 11+ cannot re-request "Allow all the time" from a dialog at all — the user is sent to Settings, so the provider exposes `refreshPermissionStatuses()` to re-read permission state when the app returns to foreground, rather than trusting the pre-detour result.
The `onboardingPageCount`/`onboardingAnimationDuration` constants the guide specifies adding to `AppConstants` were never added; page count and animation duration are hardcoded inline instead.

## T022 — Trip Tracking Screen (Active Trip) ✅
**Why:** Give a cyclist a live view of an active trip — map, distance/duration/speed, and pause/resume/stop controls — instead of a background-only recorder.
**Durable decisions:**
- Auto-navigation to the tracking screen is driven by `ref.listenManual(tripStateMachineProvider, …)` in `lib/main.dart`, transitioning only on idle/detecting → active, not by a raw `pushNamed` from a widget.
- Navigation goes through `AppNavigator` (`lib/core/navigation/app_navigator.dart`), a `NavigatorObserver` that also tracks the current route — this is what stops a repeated notification tap from stacking a second copy of the tracking screen.
- The "Trip" tab is a permanent slot in the bottom `NavigationBar` (`HomeShell` in `main.dart`), not a FAB shown only while a trip is active — the guide's FAB-only approach was rejected because with no trip running that tab is where the manual start button lives (audit #11: the app previously had no way to start a trip at all).
- Map tiles are plain OpenStreetMap raster tiles (`tile.openstreetmap.org`), matching the guide's choice, still with `flutter_map`/`latlong2` (now 8.3.2 / 0.10.1, not the pinned 7.0.2 / 0.9.0 the guide names).
**Delivered:** `lib/features/trip_detection/presentation/screens/trip_tracking_screen.dart`, `lib/features/trip_detection/presentation/widgets/{trip_map_view,trip_stats_grid,trip_control_buttons,stop_confirmation_dialog}.dart`, `lib/core/navigation/app_navigator.dart`.
**Pitfalls:** The guide's sketch of auto-navigation as a bare `Navigator.pushNamed` inside `ref.listen` would double-push on a re-render or a repeated state ping; the shipped code routes every navigation through the single `AppNavigator` instance instead.

## T023 — Trip History Screen ✅
**Why:** Give the rider a way to browse past trips, inspect one in detail with its route, and confirm or discard what auto-detection recorded.
**Durable decisions:**
- Filtering shipped as a dedicated `TripFilter` freezed model plus `trip_filter_provider.dart` and a `trip_filter_dialog.dart`, not the "optional chips" the guide sketched — filtering ended up a first-class feature, not an afterthought.
- `Trip.avgSpeed`/`maxSpeed` are stored and read as km/h, not m/s as the guide's model sketch claimed; UI formatting must not re-convert.
- `Trip.duration` is **moving time in seconds** with pauses already subtracted, tracked separately from `pauseDuration` (added later, schema v3) and `suspectedVehicle` (T053, schema v4) — neither field existed when this guide was written, and history/detail views must not treat `duration` as raw elapsed wall-clock time.
**Delivered:** `lib/features/trip_history/` (repositories, `trip_filter.dart`, providers, `screens/`, `widgets/`).
**Pitfalls:** A database row written before schema v3/v4 has no `pause_duration`/`suspected_vehicle` columns; `Trip.fromMap` treats a missing value as 0/false rather than null, so older trips silently read as "no stops, not suspected vehicle" — not an error.

## T024 — Settings Screen ✅
**Why:** Expose the T011 settings data layer (detection, battery, location, notifications, privacy, display, developer) as a usable, immediately-applying settings UI.
**Durable decisions:**
- The developer-only logging toggle is `UserSettings.auditLogEnabled` (plus `auditLogLevel`), replacing a `debugLoggingEnabled` field that nothing ever read — and it is deliberately **not** gated on `kDebugMode`, contradicting the guide's own pitfall #8 ("developer settings only in debug builds"): the point is that a tester running a release build can turn it on, ride, and export what the pipeline actually did.
- `dataCollectionConsent` is not just an analytics opt-in as the guide framed it — T034 repurposed it to gate `CaptureController`'s raw training-data capture (`lib/features/diagnostics/data/services/capture_controller.dart`), so the privacy toggle now controls whether real sensor/GPS traces get written to disk.
- Settings apply immediately with no Save button, and destructive actions (clear trips, reset settings) require a confirmation dialog — both carried through as-is.
**Delivered:** `lib/features/settings/` (`domain/models/{user_settings,detection_settings}.dart`, `presentation/screens/settings_screen.dart`, `presentation/widgets/*_settings_section.dart`, reusable `setting_section.dart`/`setting_tile.dart`/`setting_slider.dart`/`setting_radio_group.dart`).
**Pitfalls:** Full background-location permission handling was deferred out of this task to T027, per the guide's own note — don't expect the location section here to own the OS permission flow.

## T025 — Notifications & Foreground Service UI ✅
**Why:** The T005 foreground notification was bare text ("Speed: X.X km/h") with no trip-start/stop alerts, no actions, and no Android 13+ permission handling — not enough for a user to control or trust a background-tracking notification.
**Durable decisions:**
- Two Android channels, not one: `tripTrackingChannelId` (`Importance.low`, silent — it's ongoing) vs `tripEventsChannelId` (`Importance.high`, sound/vibration — it's a discrete event), so users can mute one without the other.
- Trip-start notification auto-dismisses after 5 seconds; trip-stop does not — a start alert is a heads-up, a stop alert is a summary worth leaving up.
- All three notification toggles (`tripNotificationsEnabled`, `showOngoingNotification`, `soundOnTripStartStop`) live in `UserSettings` and are read fresh on every notification call rather than cached.
- Notification taps carry a string payload (`tracking`, or `trip:<id>`) resolved through `AppNavigator`, with an unknown/id-less payload falling back to the home shell rather than doing nothing.
- Notification action callbacks (`pause`/`resume`/`stop`) are fire-and-forget wrapped in try/catch, because `handleNotificationResponse` is a synchronous platform callback — an uncaught exception there becomes an unhandled async error.
**Delivered:** `lib/features/trip_detection/data/services/notification_service.dart`, `lib/core/constants/app_constants.dart` (notification IDs/channels/texts), `android/app/src/main/AndroidManifest.xml` (`POST_NOTIFICATIONS`), `lib/features/trip_detection/services/background_location_service.dart`.
**Pitfalls:** The guide's own Phase 4 plan (a `Timer.periodic` inside the background isolate opening a fresh `ProviderContainer` to call `NotificationService.showForegroundNotification`) was not what shipped — the background isolate instead calls `service.invoke('updateNotification', …)` across the isolate boundary to the main isolate, and `NotificationService` is only awaited once at service start to guarantee the Android channel exists before `setForegroundNotificationInfo` (Riverpod is unavailable inside the background isolate at all).

## T026 — Loading States & Error Handling ✅
**Why:** Every screen hand-rolled its own error Column/Icon/Text and a bare `CircularProgressIndicator()`, retry used three different Riverpod idioms across screens, and two destructive settings actions (`deleteAllTrips()`, `resetToDefaults()`) had no error feedback at all.
**Durable decisions:**
- `ErrorView` classifies into a fixed small set (`ErrorType.notFound/network/permission/database/unknown`) with named factory constructors per type, rather than free-form error text, so every screen's error UI looks the same.
- `ErrorHandler.classifyError` checks concrete exception types before falling back to string-matching `error.toString()` — and checks `TimeoutException` before the network string match, because `TimeoutException.toString()` is just its message and would otherwise be miscategorised as a network error.
- `AsyncValueExtensions` (`errorMessage`, `errorType`, `buildErrorView`) exist so a screen can go from `AsyncValue` straight to a themed `ErrorView` without repeating classification logic inline.
- Destructive settings actions in `data_management_section.dart` are now wrapped in try/catch with a success/error snackbar pair (`AppColors.success`/`AppColors.error`), guarded by `context.mounted`.
**Delivered:** `lib/shared/widgets/error_view.dart`, `lib/shared/widgets/loading_view.dart`, `lib/core/utils/error_handler.dart`, `lib/core/extensions/async_value_extensions.dart`, `lib/features/settings/presentation/widgets/data_management_section.dart`.
**Pitfalls:** The guide assumed `TripNotFoundException` lives in `lib/features/trip_history/domain/exceptions/trip_not_found_exception.dart` — it does not exist there; it's actually defined in `lib/features/trip_history/presentation/providers/trip_detail_provider.dart`, and `ErrorHandler` imports it from that provider file.

## T027 — Permission Handler Implementation ✅
**Why:** Location permission handling existed only ad hoc via Geolocator; there was no shared service for notification (Android 13+) or future activity-recognition permissions, no rationale UI before a system prompt, and the background-location settings toggle was a TODO stub.
**Durable decisions:**
- Requests are progressive by platform contract, not preference: `AppPermission.locationAlways` is refused with `PermissionDeniedException` unless `locationWhenInUse` is already granted — Android's own two-step flow requires it.
- `requestPermission` tracks in-flight requests per `AppPermission` and throws `PermissionRequestInProgressException` on a duplicate call, so a rapid double-tap on a settings toggle can't fire two system dialogs at once.
- Permanently-denied is a distinct terminal state (`PermissionPermanentlyDeniedException`) routed to an "Open Settings" dialog rather than retried — `permission_handler` cannot re-prompt once the OS has decided the user won't be asked again.
- A rationale dialog (benefits list + optional privacy note) is shown before every optional/background request, with a `Skip`/`Not Now` path that never calls into `permission_handler` — asking without context lowers acceptance.
- `isLocationServiceEnabled` (device GPS off, distinct from permission denial) is checked before requesting location permissions and surfaces its own `LocationServiceDisabledException` with a separate "enable location services" dialog.
**Delivered:** `lib/core/permissions/` (models, services, widgets, exceptions), `lib/features/settings/presentation/widgets/location_settings_section.dart`, `test/core/permissions/`.
**Pitfalls:** None beyond the platform-contract points above — the guide's two-step Android background flow and iOS "Allow Once" caveat both match what `permission_handler` actually requires.

## T028 — Platform-Specific Configuration ✅
**Why:** The location/notification permissions from T005/T025 worked but were undocumented, and iOS 17+ App Store submission requires a Privacy Manifest that did not yet exist.
**Durable decisions:**
- Runtime API/version detection lives in `PlatformInfoService` (`lib/core/platform/services/platform_info_service.dart`) rather than scattered `Platform.isAndroid` checks, so callers can branch on `isAndroid11Plus`, `isAndroid13Plus`, `isIos17Plus`, etc. (`lib/core/platform/models/platform_info.dart`).
- `PlatformInfo`'s helper getters live in an `extension PlatformInfoExtensions` outside the freezed class, per the project's freezed convention.
- `android:allowBackup="false"` was added on the `<application>` tag to keep the trip SQLite database (precise route history) off Google Auto Backup / `adb backup` — not in the original guide, added to match the "data stays on device" privacy promise.
- iOS Privacy Manifest (`ios/Runner/PrivacyInfo.xcprivacy`) declares Location and User Defaults access but deliberately omits a Device ID declaration (added later, T037) since nothing in the app reads a device identifier.
**Delivered:** `lib/core/platform/models/platform_info.dart`, `lib/core/platform/services/platform_info_service.dart`, `lib/core/utils/platform_config_validator.dart`, `android/app/src/main/AndroidManifest.xml`, `ios/Runner/Info.plist`, `ios/Runner/PrivacyInfo.xcprivacy`, `test/core/platform/platform_info_test.dart`.
**Pitfalls:**
- The User Defaults privacy-manifest reason code was originally declared `1C8F.1` (App Group access) but that's wrong for this app — AutoRide has no App Group / entitlements file. It was corrected to `CA92.1` ("accessible to the app itself") on 2026-09-03; if re-adding any UserDefaults-touching feature, use `CA92.1`, not `1C8F.1`.
- `UIBackgroundModes` in Info.plist carries only `location` and `fetch` today — the guide's proposed `processing` entry was never added; don't assume it's there.

## T036 — App Icons & Splash Screen ✅
**Why:** the Flutter template icons/splash were still in place; App Review rejects placeholder artwork, and a launcher icon/splash needs both iOS and Android-specific derived formats.
**Durable decisions:**
- All platform assets are derived from a single `assets/icon/source-1024.png` by `scripts/generate-icons.sh`, never hand-edited, so replacing the artwork is one file swap + one command.
- Android adaptive icon needs separate background/foreground layers (`icon-background.png`, `icon-foreground.png`); iOS uses the flattened `icon-1024.png` with its own squircle mask.
- Foreground artwork is sized (600px of 1024px layer) to stay inside Android's 61% safe circle so no bike-wheel edge is clipped by a circular launcher mask.
- Splash uses one solid colour (`#1E98DD`, the gradient's centre) rather than the gradient, because Android 12+'s `windowSplashScreenBackground` only accepts a single colour and this keeps launch consistent across platforms/generations.
- `assets/icon/` is deliberately NOT declared under `flutter:` in `pubspec.yaml` — these are build-time generator inputs, not runtime assets, to avoid shipping ~2MB of unused PNGs.
**Delivered:** `assets/icon/`, `scripts/generate-icons.sh`, `flutter_launcher_icons.yaml`, `flutter_native_splash.yaml`, generated `android/app/src/main/res/mipmap-*/` and `drawable*/`, `android/app/src/main/res/values{,-night}{,-v31}/styles.xml` (`windowSplashScreenBackground=#1E98DD` confirmed), `ios/Runner/Assets.xcassets/{AppIcon,LaunchImage,LaunchBackground}.*`.
**Pitfalls:** `flutter_launcher_icons` corrupts the Xcode build setting `ASSETCATALOG_COMPILER_GENERATE_SWIFT_ASSET_SYMBOL_EXTENSIONS` (writes the icon name into a boolean field) — the generate script auto-repairs it with `sed`. `flutter_native_splash` reformats and re-indents the entirety of `ios/Runner/Info.plist` on every run (a 152-line diff for a one-key change) and is not auto-reverted because the file carries hand-written comments from other tasks — the script only warns; `git checkout ios/Runner/Info.plist` is the fix. The route's orange dots disappear below ~72px in the launcher icon — accepted, the bicycle carries the icon.
